在多租户、高并发的分布式存储系统中，如何高效利用多轨 RDMA 网络带宽，同时保障不同优先级请求的服务质量，是一个极具挑战性的问题。Mooncake 采用了简单的 Round-Robin 法则进行分配，无法依据网络的实际情况进行优化调度。Mooncake TENT 通过 Slice Spraying（分片喷射）和 QoS（服务质量） 两大机制，巧妙地解决了这个问题。
下面我们将从设计原理、代码实现和配置使用三个维度，深入剖析这两项核心技术。相关的更新参考我们将要合入的 PR https://github.com/kvcache-ai/Mooncake/pull/2048

## 1. 为什么要做这个优化

由于 Mooncake TE 等现有引擎普遍依赖于静态且无法感知系统状态（state-blind）的路径选择策略，面对非均匀的网络负载时，无法充分利用空闲容量，从而导致了“带宽闲置与浪费”（bandwidth stranding）问题。

### 1.1 多租户流量干扰

在一些应用场景中，底层的互连网络需要同时承载两类流量：对延迟极度敏感的 MoE 专家并行流量（即“老鼠流”，mice flows）和高吞吐的 KVCache 迁移流量（即“大象流”，elephant flows）。二者并行运行会产生性能的退化。目前常见的做法是通过刚性划分工作负载来缓解两者的干扰。例如，将 MoE 流量限制在节点内的 NVLink 中，而将 RDMA 网络留给 KVCache 迁移。这种静态隔离不仅限制了 MoE 跨越单节点边界的扩展能力，还导致了系统资源的严重低效利用。在跨节点 MoE 专家并行等不可避免要共享资源的场景下，这种对状态的盲目性经常导致对延迟敏感的关键路径信号被大象流死死堵住。结果是，即使其他互补的物理路径正处于空闲状态，总的总聚合带宽也实际上被闲置和浪费了。

### 1.2 慢速断点拖慢大象流传输
在 DeepSeek-V3 等模型中，缓存与计算比高达 22 GB/PFLOP，这意味着 KVCache 的数据搬运也直接决定了智能体（agentic）推理任务的关键执行路径。我们的生产环境遥测数据也表明，在现有引擎（例如基于 UCX 后端的 NIXL 和 Mooncake TE）中，大规模的 KVCache 传输频繁受到这种“状态盲目条带化”（state-blind striping）的困扰。由于这些引擎仅通过静态哈希或 NUMA 优先级来分发数据块（chunks），它们根本无法应对生产环境中常见的软故障（grey failures）和喧闹邻居（noisy neighbors）问题。一旦将数据分片分配给这些性能降级或跨 NUMA 的轨道（rails），就会产生拖后腿的“慢节点”（stragglers），从而引发队头阻塞（HoL blocking），导致整个传输任务停滞不前。

我们在一个由 8 轨 200 Gbps 构成的 RDMA 网络上通过实验复现了这一现象。我们使用 4 个提交线程发起了 1 MB 的读取请求，并将传统的轮询（round-robin）基线方法与我们基于遥测驱动的调度器进行了对比。在轮询模式下，连接到远端 NUMA 域的轨道表现出了明显更高的分片服务时间；这些特定轨道上的队列积压直接推高了整个请求的 P99 延迟。相反，当调度器利用实时遥测数据（如排队字节数和完成延迟）来引导分片避开这些拥堵轨道时，网络吞吐量显著提升，尾部延迟大幅下降，整个网络内部的传输进度也保持了均衡。

![](/images/tent-internal-slice-spraying-and-qos/slice-spraying-motivation.png)

由此可见，在同样暴露了静态绑定缺陷的异构网络中，这种对状态盲目的条带化划分，会将物理层面的非均匀性直接放大为性能暴跌的断崖。为了解决这一痛点，我们需要将所有轨道视为一个统一的资源池，将数据传输拆分为更细粒度的分片，并基于能感知遥测状态的成本模型对每个分片进行动态调度。

## 2. Slice Spraying 算法

### 2.1 基线实现

Mooncake Transfer Engine 采用了简单轮询设计原则。在这种方案中，设备选择逻辑非常直接——系统维护一个本地计数器，每次有新的传输请求时，就在当前 NUMA 层级的设备列表中按顺序选择下一个设备。只有在当前 NUMA 层级没有可用设备时，才会回退到远程 NUMA 层级。

```cpp
// 简单轮询策略
thread_local int id = 0;
for (size_t rank = 0; rank < Topology::DevicePriorityRanks; ++rank) {
    auto& list = entry->device_list[rank];
    if (list.empty()) continue;
    chosen_dev_id = list[id % list.size()];
    id++;
    return Status::OK();
}
```

这种设计的核心优势在于确定性和可预测性。由于不需要维护任何负载状态，也不需要执行复杂的计算，系统的运行时开销几乎为零。在设备性能相同、负载分布均匀的理想环境中，这种方案能够完美地完成工作。

然而，其局限性同样明显。面对现实世界中的复杂性——异构的链路质量、动态变化的负载条件、以及跨 NUMA 访问带来的延迟差异——这种静态轮询策略显得无能为力。当某些链路因拥塞而性能下降时，轮询算法依然会将相同数量的请求发送给它，导致整体吞吐量受损。这一点可以从前面的图中看出。

### 2.2 早期 Mooncake TENT 实现

为了应对基线实现的局限性，Mooncake TENT 尝试引入一套基于自适应反馈的智能调度算法。这套算法的核心思想是通过估计请求到每个目标网卡预期的送达时间，选择一个尽可能快的本地网卡进行交付。远端网卡则采用与 Mooncake TE 相似的原则，在满足 rank 匹配的情况下尽可能一比一匹配。

在这个版本中，本地每张网卡的预期送达时间做此估计：
$$
predicted_time = weight \times ((inflight\_bytes + request\_bytes) / bandwidth \times \beta_1 + \beta_0)
$$
该算法采用了一个双参数模型来预测传输时间：beta0 表示固定延迟（如 PCIe 传输开销、连接建立时间等），beta1 表示有效带宽的修正系数。weight 是一个常量，当本地存储介质和网卡的距离（NUMA等）较长时，会通过较高的系数降低对该卡的选择几率。对于每个待处理的传输请求，系统会计算所有候选设备的预测完成时间，并选择表现最优的那个。预测公式综合考虑了当前设备的活跃负载、理论带宽，以及通过历史学习得到的修正参数。

为了保证参数能够适应不断变化的网络条件，算法实现了一套精细的更新机制。每当一次传输完成，系统会记录实际耗时与预测时间的差异，并采用指数平滑的方式更新每张网卡分别对应的 beta0 和 beta1 参数。

然而，当我们将这个模式进行落地验证的时候，我们发现这套精心设计的系统在实际运行中暴露出了一些问题，其性能在某些情况下甚至不如基线的水平。首先，双参数模型增加了调优的复杂性——运维人员需要同时理解 beta0 和 beta1 的含义，并且分别设置适当的阈值，才能有效地调整系统行为，避免估计失真。

### 2.3 优化后 Mooncake TENT 实现

在总结了早期实现的得失之后，我们提出了一种回归本质的优化方案。新方案的核心思想是：简化模型，保留精髓，增强可扩展性。

本地每张网卡的预期送达时间做此估计：
$$
predicted\_time = \frac{inflight\_bytes + request\_bytes}{ewma\_bandwidth} \times weight
$$
注意，我们不再使用容易放大偏差的 beta0、beta1 双参数了。相反，我们将其简化为单一的 EWMA 带宽估计。每个设备只需维护一个带宽估计值，每当传输完成时，系统根据观测到的实际带宽更新这个估计值。
为了防止估计值偏离合理范围，系统还设置了边界限制，将 EWMA 值约束在理论带宽的 10% 到 1000% 之间。这种保守的设计确保了即使出现异常观测，系统也不会做出过于极端的决策。

同时，我们特别为大请求采取了比例分配的策略。对于切片数较多的请求，在可用设备中按一定比例进行分配有助于提升端到端带宽并降低时延。因此，我们不采用“每个 Slice 独立决策所用的本地网卡”，而是通过按比例分配给多个候选设备的方法，充分利用了多轨 RDMA 的聚合带宽。比例的选择主要基于前面测量的 predicted_time 而定。predicted_time 较小的设备可占据较大的份额。

```cpp
// 按设备容量比例分配
double total_weight = sum(c.score for c in candidates);
for (const Candidate& c : candidates) {
    uint32_t allocation = (c.score / total_weight) * num_slices;
    for (uint32_t i = 0; i < allocation; ++i) {
        slice_dev_ids.push_back(c.dev_id);
    }
}
// 剩余分片分配给最优设备
uint32_t remaining = num_slices - slice_dev_ids.size();
for (uint32_t i = 0; i < remaining; ++i) {
    slice_dev_ids.push_back(best.dev_id);
}
```

从整体上看，优化后的实现通过简化模型、减少状态同步开销、增强多路径支持，在性能和可维护性之间取得了更好的平衡。

## 3. 服务质量保障（QoS）机制
在多租户、混合负载的分布式存储环境中，如何确保关键操作的响应时间，同时避免后台批量传输被无限期延迟，是一个极具挑战性的问题。

### 3.1 同一个实例内的 QoS
为了提供更可预测的性能保障，TENT 支持严格优先级调度。在这种模式下，工作线程始终先处理高优先级队列，只有当高优先级队列为空时，才会处理中优先级队列，以此类推。这种设计确保了高优先级请求永远不会等待低优先级请求，从而提供了确定性的性能保障。

严格优先级调度的实现非常直观。在每次调度循环中，系统按优先级从高到低的顺序检查各个队列，一旦发现非空队列就立即处理其中的请求，然后跳出循环。这种策略保证了在任何时刻，如果系统中有高优先级的工作在等待，它们一定会优先得到服务。

但是，严格优先级调度也带来了一个新的问题：低优先级饿死。在高优先级请求持续不断的场景下，低优先级队列中的请求可能永远无法得到执行机会。这对于后台批量传输等非关键任务来说是不可接受的。Mooncake TENT 引入了一套超时优先级提升机制。每个工作线程会定期检查各个优先级队列，如果发现某个请求等待时间超过了配置的阈值（默认 10 毫秒），就会将其提升到更高的优先级。等待过久的中优先级请求会被提升到高优先级队列，而等待过久的低优先级请求则会被提升到中优先级队列。这种渐进式的提升策略确保了即使在高负载情况下，所有请求最终都能得到服务。

这套机制的实现巧妙地利用了时间戳信息。每个请求在被加入队列时都会记录其入队时间（enqueue_ts），在检查提升条件时，系统只需要比较当前时间与入队时间的差值是否超过阈值即可。为了避免频繁的检查开销，系统使用了一个简单的优化：记录下次检查时间，只有到达该时间点时才执行真正的检查逻辑。

### 3.2 多进程间的 QoS 协调
在单进程环境中，严格优先级调度配合防饥饿机制已经能够很好地工作。然而，当系统运行多个独立进程时，每个进程只关注自己的请求调度，可能导致某个进程的低优先级请求持续占用网络带宽，影响其他进程的高优先级请求。

为了解决这个问题，Mooncake TENT 设计了一套跨进程时隙协调机制。系统在共享内存中维护一个全局时隙状态，所有参与进程通过这个状态进行同步。时隙机制将时间划分为固定长度的周期，每个周期包含三个时隙：

- 时隙 0：只允许高优先级请求
- 时隙 1：允许中优先级和高优先级请求
- 时隙 2：允许所有优先级的请求

时隙的长度是可配置的，默认为 2 毫秒，因此完整的周期长度为 6 毫秒。一个后台线程负责定期旋转时隙，确保所有进程看到相同的当前时隙值。在处理请求之前，工作线程会检查当前时隙是否允许该请求的优先级，如果不允许则跳过处理。

这种设计的好处是显而易见的。高优先级请求在每个时隙都能获得服务，但时隙 0 为它们提供了独占的执行窗口，确保了最低的延迟。中优先级请求在三分之二的时隙中可以获得服务，而低优先级请求则只在三分之一的时间中被允许执行。这种既保证服务质量又避免完全饿死的平衡，正是时隙机制的核心价值。

Mooncake TENT 的 QoS 机制提供了丰富的配置选项，允许运维人员根据具体场景进行调优。对于延迟敏感的关键应用，可以缩短时隙间隔到 1 毫秒，为高优先级请求提供更频繁的独占窗口。对于吞吐量导向的批量处理任务，可以将时隙间隔延长到 10 毫秒，给予低优先级请求更多的执行时间。防饥饿超时的设置同样需要根据应用特点进行调整。太短的超时会导致频繁的优先级提升，削弱优先级机制的意义；太长的超时则可能导致低优先级请求的等待时间过长。默认的 10 毫秒是一个折中的选择，适用于大多数通用场景。

### 3.3 性能实测 

![](/images/tent-internal-slice-spraying-and-qos/qos.png)

我们在 H20 测试床上评估了 TENT 的 QoS 能力。实验使用两个并发进程，每个进程采用 8 个提交线程以跑满 $4 \times 400$ Gbps 的 RoCE 网络。第一个进程发起对延迟敏感的”老鼠流”（64 KB 的元数据同步，始终设为高优先级），第二个进程则产生重吞吐的”大象流”（64 MB 的 KVCache 迁移）。我们对比了四种配置：No QoS（无 QoS）、QoS (High+Medium)（高+中优先级 QoS）、QoS (High+Low)（高+低优先级 QoS）以及 Solo（单任务独占）执行基线。高优先级意图利用优先级时段轮转机制进行传输，同时主动抑制低优先级流量，以保持较低的物理队列深度。

结果表明，老鼠流的 P50 延迟降低了 15.1%。这主要是通过有意的时段限流来缓解进程间竞争实现的。该能力的实现得益于引擎的优先级时段轮转机制——它在向高优先级分片倾斜的同时，依然确保了整体传输能持续推进，从而防止低优先级流量发生饥饿。值得注意的是，P99 延迟保持了稳定，这是因为当设备轮转到“接受低优先级”状态时，它会接收所有分片而不论其优先级如何，从而确保高优先级意图绝不会被后台流量无限期地卡死。这些结果证实，TENT 具备 QoS 感知的 Slice Spraying 技术能够有效优先处理对延迟敏感的关键老鼠流（例如 MoE 专家并行流量），直接有助于缩短整体的首字延迟（TTFT）。
